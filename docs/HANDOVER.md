## 5. 分析を生成する（API 課金なし）

生成だけを Claude のセッションで行い、結果を `--replay` で取り込む。**検査は生成元に
関係なく同じように走る**ので、取り込み経路が変わっても出力の規律は変わらない。

```bash
AS_OF=$(python3 -c "import sys;sys.path.insert(0,'src');from future100 import timeutil;print(timeutil.now_str())")
python3 scripts/analyze_sector.py --sector <id> --as-of "$AS_OF" --show-prompt
# 応答を {"consensus": {…}, "independent": {…ANALYSIS_SCHEMA 全体…}} で保存
python3 scripts/analyze_sector.py --sector <id> --as-of "$AS_OF" --replay out.json

python3 scripts/analyze_chain.py --sector <id> --as-of "$AS_OF" --show-prompt
# {"wave": {…}, "supply_chain": {…}}
python3 scripts/analyze_chain.py --sector <id> --as-of "$AS_OF" --replay chain.json
```

`--as-of` を固定するのは、根拠の集合がずれると `event_id` が合わなくなるため。

**罠**: `--replay` ファイルの 2 番目のキーが持つのは「2 回目の呼び出しの応答全体」で
あって、独自見解の部分だけではない。`ANALYSIS_SCHEMA` は
independent / phase / growth / scenarios を含むので、`"independent"` キーの中に
もう一段 `"independent"` が入る形になる。

## 6. 実測で見つけた罠（同じ失敗を繰り返さないために）

設計判断のうち、机上では分からず実データで初めて分かったものを残す。

### 重複統合
- **同一 URL の一致以外は、別ソース間でのみ使う。** 同一ソース内で表題や本文の
  類似で統合すると、同じ発行元が同日に出す別々の契約公告 22 件が 1 件に潰れた。
- **すべての一致判定に発生日の枠を掛ける。** 日付の枠が無い `content_hash` 一致で、
  4 か月ぶんの日銀の月次報告が 1 件に統合され、観測が 3 件消えていた。
- **`cluster_id` は `event_key` ではなく `event_id` から導出する。** 統合しないと
  判定したのに同じクラスタ ID になる衝突が起きた。
- 類似度は jaccard ではなく containment。言い換えの同一報道が jaccard 0.46 に
  なり、閾値 0.72 を越えられなかった。

### キーワード判定
- **語境界を要求する。** `"series a"` が `"series **a**nd"` に一致し、Samsung の
  新製品記事が資金調達シグナルとして数えられていた。
- **セクターのキーワードは複合語にする。** `transformer` / `space` / `fusion` /
  `optical` は機械学習の論文に当たり、電力・送配電の根拠 25 件のうち 24 件が
  無関係な論文だった。
- **キーワードで拾えるとは限らない。** arXiv の論文判定はキーワードでは 41% しか
  拾えず、論文数の比較が実数の 4 割で行われていた。ソースの性質で決まるものは
  `default_signal_types` でソース単位に付与する。
- **統計からキーワードでシグナルを立てない。** 「特許出願件数」という系列名に
  判定をかけると、年次統計を 1 本取り込んだだけで特許シグナルが 12 件立ち上がる。

### 発生時刻
- **`observed_at` を発行日に書き換えない。** 過去分を取り込んでも「そのとき見て
  いた」ことにはしない。今日より前の `as_of` で再生したときに過去分が見えないのが
  正しい (§37)。
- **`as_of` は収集の後に確定する。** 収集の前に確定させると、その回に取り込んだ
  観測が「未来の情報」になって CI が落ちた。
- **記録の更新時刻を発生時刻に使わない。** USAspending の `Last Modified Date` は
  20 年前に始まった契約の修正が 2001 年の日付で返ることがあった。契約が結ばれた日
  (`date_signed` / `Base Obligation Date`) を使う。
- 日時で返る対象期間は日付に丸める。入札日 `2026-08-19T00:00:00` の `00:00` は
  「その日」以上の情報を持たず、残すと同じ日が別の期間として並ぶ。

### 統計の取り込み
- **観測の同一性は「系列 + 期間 + 値」。** 取得 URL には期間指定が入るため、URL を
  そのまま同一性に使うと年が変わるたびに同じ数値が新しい観測として湧く。
- **識別子は URL のフラグメントに置かない。** `canonical_url` は正規化でフラグメントを
  落とすため、系列の全期間が 1 つのクラスタに統合される。クエリに置く。
- **速報値の改訂は上書きせず別の観測として残す。**
- **系列名に区分を織り込む。** 後段は `quantities.label` で系列を束ねるため、国名を
  落とすと 7 か国の値が 1 本の系列に見える。逆に識別専用の区分（入札の CUSIP）を
  名前に入れると、1 点しかない系列が銘柄の数だけレポートに並ぶ（`label_fields` で絞る）。
- **HTTP 200 のまま本文で失敗を告げる API がある。** BLS はキー無しの日次上限超過を
  200 で返す。0 件と区別しないと、取得できていない期間が「統計が無かった」として残る。
- **応答が上限で切られるソースは区間を細かくする。** USAspending は 1 応答 100 件で、
  7 日まとめて取ると日次収集より粗い件数になり baseline が過小になる。

### 過去分の取り込み
- **0 件の日で打ち切らない。** arXiv は週末に announce が無く、これを失敗として扱うと
  35 日ぶんの取り込みが最初の週末で止まる（`EmptyPayload` で型を分けてある）。
- **期間を指定する手段が無いソースを「取り込んだ」ことにしない。** 同じ最新フィードを
  区間の数だけ取り直して記録するのが最も危険な失敗になる。
- **穴の空いた範囲を観測済みにしない。** 途中で落ちた区間から先は取り込めていない。

### 根拠の選び方
- **1 ソースの当たり日で上限を埋めない。** 信頼度順・新しい順に 150 件取ると、1 日
  200 本流れる論文フィードが枠を全部使い、実測で 150 件中 146 件が同じ日の arXiv
  だった。ソース × 日ごとに 4 件までに絞ってから埋める。

### 取得間隔
- **1 日以上の間隔は経過時間ではなく日付の差で数える。** 日次ジョブの起動時刻は
  数十分から数時間ずれるため、経過時間で締め切ると「23 時間しか経っていない」を
  理由に日次ソースを丸ごと落とす日が出る。落とした日は観測履歴に穴が開く。

## 7. 残課題（効く順）

1. **観測履歴を貯める。** これ以外に代えはきかない。RSS しか出さないソースが寄与する
   topic は、日次収集が baseline 期間（直近 7 日 + その前 28 日）に届くまで判定保留の
   ままになる。
2. **系統運用者 (TSO) の設備投資計画。** §13 のボトルネック検証に最も効く一次情報。
   ENTSO-E 透明性プラットフォームが最有力だが XML のみで JSON 提供が無く、無償の
   セキュリティトークン申請と XML コレクタが要る（`src_entsoe_transparency` に無効で登録済み）。
3. **財務省プレスリリース。** 買い戻し規模の変更・四半期リファンディング声明が出る
   場所。RSS も JSON API も無い（`rss/press.xml`・`jsonapi` ともに 404 を実測）ため
   HTML コレクタが要る。いまは「発表の結果が数字にどう出たか」は取れるが
   「発表そのもの」は取れない。
4. **SEC Form D の過去分。** `browse-edgar?action=getcurrent` は現在の届出しか返さない
   ため遡れない。full-index の取り込みが要る。
5. **予測の登録。** §40-43 のループは、構造評価から検証可能な予測を作って期日が来て
   初めて回り始める。いまは予測 0 件で精度を測る対象が無い。
6. 到達性で無効中のソース: METI / JPO / IEA / TSMC（403）、USPTO・EIA・BLS（要キー）。

## 8. 触るときに壊しやすいところ

- `config/signal_rules.json` と `config/known_sectors.json` を変えたら
  `python3 scripts/normalize.py --rebuild`。raw は不変なので何度でも作り直せる。
- **索引（`data/index/`）はマージで衝突する。** raw は追記のみなので両方の観測が
  揃っている。片方を選ぶのではなく、`storage.rebuild_raw_index()` →
  `normalize.py --rebuild` で作り直すのが正しい。
- 日次レポートと signal 窓は毎回 `as_of` が変わるため、main とのマージで必ず衝突する。
  再生成して解決する（どちらも導出物）。
- スコアは内部指標。ランキングを出力しない (§44-46)。レポート生成時に機械的に
  検査しており、違反すると保存前に例外で止まる。
