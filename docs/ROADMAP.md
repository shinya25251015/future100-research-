## Phase 1（完了）

- `scripts/init_structure.py` … ディレクトリの冪等生成。`--check` で CI からも検査できる。
- `schemas/*.schema.json` … 正準データモデル（JSON Schema draft 2020-12）。
- `src/future100/invariants.py` … JSON Schema では表現しきれない仕様書の規律をコードで強制。

データモデルの設計方針は 4 点に集約される。

1. **観測時刻と発生時刻を分ける** — `observed_at`（本システムが見た時刻）と `event_at`（起きた時刻）を
   全レコードに持たせ、分析側は必ず `as_of` を渡して読む。これが Look-ahead Bias 防止の唯一の仕組み (§37)。
2. **事実と推論を分ける** — `claims[].type` が `observed` か `inferred` か。`inferred` は `basis` 必須 (§17-19)。
3. **値と根拠を対で持つ** — 構造指標も市場規模も `{ value, rationale, evidence }` の形。根拠のない数値は書けない (§35-38)。
4. **raw は不変** — 正規化規則を変えたら `normalize.py --rebuild` で作り直す。当時観測できた情報だけで
   何度でも再現できる状態を保つ (§48-51)。

   | シグナル種別 | 状況 |
   |---|---|

   | procurement | USAspending（金額付き）+ 米国防契約公告。229 件/日 |
   | export_control | 大統領令 + Federal Register。関税・輸出規制の起点を押さえている |
   | subsidy / government_budget | Federal Register 経由。日本・EU 分が薄い |
   | capex_guidance | NVIDIA / Intel / Samsung / Microsoft の広報 (§7)。TSMC は 403 |
   | new_standard | IEEE Spectrum・企業広報から間接的。規格団体の直接取り込みが未実装 |
   | vc_investment | SEC Form D。`FUTURE100_CONTACT_EMAIL` の設定が必要 |
   | patent | **未取得**。PatentsView v1・data.uspto.gov とも API キー必須（旧 api.patentsview.org は廃止） |
   | job_posting | **未取得**。無償で使える公開 API が見当たらない |
   | new_facility / supply_contract | 企業広報から拾えるが、決算・IR 資料の直接取り込みが未実装 |

   残る課題は次の 3 点。
   - **日本の政策一次情報** — 経産省・特許庁・外務省とも実行環境から HTTP 403（同じ遮断パターン）。
     国内 IP からの実行が必要。官報 (kanpo.go.jp) は 200 が返るが、日付ベースの画面遷移が必要で
     汎用の HTML コレクタでは取れない。
   - **特許** — API キーを取得すれば `src_uspto_patents` を有効化できる状態にしてある。
   - **企業 IR / 決算 / 中国・EU 規制当局** — `json_api` の mapping で大半は追加できる。
     TSMC は 403 のため台湾証券取引所の公開情報 (MOPS) 経由を検討する。
2. **HTML コレクタ** — `src/future100/collect/html.py` に実装し `kind: "html"` を登録する。
   ただし現時点で確認できた対象が無く、着手は保留している。BIS は実行環境から接続タイムアウト、
   官報は日付ベースの画面遷移が必要で汎用コレクタでは取れない。
   対象が確定してから作る（動かす当てのないコレクタを先に作らない）。
3. **重複統合の精度 (§38)** — 判定は「同一 URL」だけが同一ソース内でも有効で、
   本文一致・表題一致・文面類似はすべて**別ソース間でのみ**適用する。
   一次情報源（契約公告・官報・規則公示）は同じ発行元が同じ日に同じ表題・同じ定型文で
   別件を大量に出すため、同一ソース内の一致は「同じ出来事」を意味しない。
   実測では連邦契約 22 件が 1 件に潰れていた。
   現在の稼働ソースは互いに素な一次情報源のため統合は 0 件で、これが正しい状態。
   一般メディア（Tier 2/3）を足すと初めて機能し始める。既知の制約が 2 つある。
   - 文面比較用トークンを永続化していないため、**同じ出来事の言い換え記事が別々の日の実行で
     届いた場合は統合されない**。日次収集では全ソースを同一バッチで取得するので実務上の大半は
     捕捉できるが、後追い報道の多い Tier 2/3 メディアを増やすと問題になる。
     対策は固定長フィンガープリント（MinHash 等）の永続化。
   - 同一実行内の比較が全クラスタ総当たり O(n²)。1 日ぶんなら問題ないが、
     大量の過去データを一括投入するときは転置インデックスが要る。
4. **カテゴリ分類とシグナル判定の精度** — category は「ソース定義の既定値」で、1 ソースが
   複数領域を出す場合に粗い。シグナル判定のキーワードも粗く、`new_standard` の "standard" のように
   一般語に当たる規則が残っている（語境界は実装済みで、"series a" が "series and" に当たる問題は解消）。
   本文からの分類（規則 → LLM）に置き換える。ここで初めて LLM を使う。
5. **収集の定期実行** — cron / GitHub Actions で日次実行し、失敗ソースを検知する。

## Phase 3（セクター分析）— 設計

Phase 3 は「イベントの山」から「構造の評価」に変換する層で、2 段構えにする。

### 3-1. Early Signal Detection (§10) — 完了

```
src/future100/signals.py       build_window(topic, window, as_of) -> SignalWindow
scripts/detect_signals.py      集計と data/signals/ への保存
```

- `data/events/` を `as_of` で絞り（`is_cluster_primary=true` のみ）、`signal_types` × 期間で集計する。
  可視性は `observed_at`、期間の割り当ては `event_at`。「いつ起きたか」で数え「いつ知ったか」で絞る (§37)。
- 判定は件数の絶対値ではなく **同時増加**。既定は直近 7 日を、その前 28 日を 7 日ぶんに割り戻した
  baseline と比較し、2 種別以上が 2 ソース以上で増えたときだけ発火させる。
- baseline が 0 のときは増加率を定義しない（0 除算を大きな数で誤魔化さない）。

**観測開始による偽シグナルの遮断（実データで最初に踏んだ罠）**

初回実行で「AI / 計算基盤: paper=338 対 baseline 0.25、score 93.3」という強烈なシグナルが出たが、
これは arXiv を*その日に初めて取得した*ことによるもので、世界の変化ではない。
収集開始直後はどのソースも baseline 期間の件数が構造的に 0 になり、**すべてが急増して見える**。

対策として `coverage` を全 SignalWindow に持たせた。寄与ソースごとの観測開始時刻を記録し、
baseline 期間の開始より後に観測を始めたソースが 1 つでもあれば `baseline_covered=false` とし、
`threshold_met` を立てない。`invariants.check_signal_window()` がこの規律を強制する。
baseline 期間ぶん（既定 28 日）収集を続ければ自動的に解消する。

現状の実行結果は **0/16 発火・14 件が判定保留**。これが観測 1 日目の正しい答えである。

- しきい値を超えた topic のうち、既知セクターに紐づかないものが §12 Emerging Sector 候補になる。
- この層に LLM は要らない。**なぜ増えたか**を説明するのが次の層。

### 3-2. セクター構造評価 (§8-9, §20-34) — 完了

```
src/future100/sector_analysis.py   build_bundle → render_prompt → draft_profile → review
scripts/analyze_sector.py          根拠の内訳とプロンプトの確認
```

LLM に任せるのは**推論だけ**で、入力の組み立て・出力の検証・保存の可否はこちら側が持つ。

- **入力** — as_of 以前に観測したイベントのみ、重複の代表イベントのみ (§37-38)。
  保有銘柄はデータモデル上どこにも存在しないため、構造的に混入し得ない (§1)。
- **呼び出しの分離** — コンセンサスと独自見解を別々のプロンプトで生成する。
  同一呼び出しで両方書かせると独自見解がコンセンサスに引きずられる (§34)。
- **出力の検証** — `review()` が 3 つを通す。スキーマ適合、仕様書の不変条件
  （3 シナリオ・撤回条件・確率と規模の分離）、そして**根拠の実在性**。
  最後のものが最重要で、生成物が引いた event_id が渡した bundle に無ければ却下する。
  架空の観測の上に以降の分析すべてが積み上がるのを防ぐ。
- 生成器は `Generator = Callable[[str], str]`（プロンプト → JSON 文字列）として
  差し替え可能。未接続の環境でも入力の組み立てと検証は単体で動く。

`src/future100/generators.py` が Claude API 実装。構造化出力 (`output_config.format`) で
スキーマ適合の JSON を保証し、拒否 (`stop_reason=refusal`) を content 読み出し前に処理する。
それでも `review()` は通す — スキーマが保証するのは形であって、根拠の実在性や
撤回条件の有無という仕様書の規律ではない。

```bash
export ANTHROPIC_API_KEY=...
python3 scripts/analyze_sector.py --sector sec_ai_compute --generate
```

検査を通った場合のみ `data/sectors/` に保存する。`--replay` で保存済みの生成結果を
読み直せるので、検証だけを API 抜きで何度でも回せる。

## 観測履歴の永続化

日次収集を CI で回す場合、コンテナは毎回破棄されるため **観測履歴をリポジトリに残さないと
baseline が永久に貯まらない**。そのため `data/` を git 管理下に置き、保存形式を git に合わせて設計した。

| 種類 | 形式 | 1 日あたり | 設計理由 |
|---|---|---|---|
| raw | `data/raw/YYYY-MM-DD/<source_id>.jsonl.gz` | 約 400KB / 9 ファイル | 1 文書 1 ファイルだと年 20 万ファイルになる |
| events | `data/events/YYYY-MM-DD.jsonl` | 約 1.1MB | 当日ぶんにのみ追記し、過去ファイルを書き換えない |
| signals | `data/signals/sig_<topic>_<date>.json` | 約 88KB | 日付入りの新規ファイル |
| index | `data/index/<name>/YYYY-MM-DD.json` | 約 100KB | 発生日で分割。1 枚の索引を毎日書き換えると差分が積み上がる |

合計およそ 700KB/日（年 250MB 程度）。年単位で肥大化した場合は古い年をアーカイブブランチに
分離する。`data/index/` はすべて派生データで、raw と events から再生成できる。

**raw は不変。** 正規化の進捗は `data/index/normalized/` に置き、raw のレコードには一切書き込まない。
正規化規則を変えたら `normalize.py --rebuild` で events を作り直す。

## Phase 4（サプライチェーン・ボトルネック・波及）— 完了

```
src/future100/chain_analysis.py   build_bundle → render_prompt → draft → review
scripts/analyze_chain.py          プロンプト確認と生成
```

Phase 3-2 と同じ構成（入力の組み立て → 呼び出し → 検証）。この層に固有の規律は 3 つ。

- **観察と推論を分ける** — 各波及段の `claim_type` が observed か inferred か。
  inferred には根拠 (basis) と撤回条件 (falsifier) を要求する (§17-19)。
- **波が進むほど確信度は上がらない** — 第 n 波の `causal_confidence` が第 n-1 波を
  上回っていたら検査で弾く。推論を重ねるほど確からしくなると主張しているのと同じため (§19)。
- **受益者は類型で書く** — ボトルネックの `monetizer_type` に個別銘柄・ティッカー・
  証券コードが入っていないか機械的に検査する (§1, §44-46)。

セクタープロファイルが無いセクターでは分析を始めない。連鎖分析は
「そのセクターで何が起きるか」の上に積む推論なので、土台が無い状態では意味を持たない。

## Phase 5（市場規模・シナリオ）— 一次統計の取り込みまで完了

シナリオ 3 本（撤回条件つき）は Phase 3-2 が生成する。数値を受け入れる側の規律は
`invariants.check_market_size` に固定してある。

- **出所のない市場規模を残さない** — 数値があるのに evidence が空なら弾く (§35-38)。
  未推計を 0 のまま置くのは正しい状態であり、違反ではない。
- **シナリオ間の順序を検査する** — 同じ年で bear <= base <= bull が壊れた予測は読めない (§9)。

### 一次統計コレクタ (`json_series`)

統計は記事と壊れ方が違う。1 系列 = 期間ごとの数値の列で、同じ URL の中身が毎月増え、
ときに過去の値が改訂される。そのため次の規約で取り込む。

- **1 データ点 = 1 観測。** 数値は単位と対象期間を伴って `quantities` に構造のまま入る。
  本文に書いた数字を後から拾い直すと単位と期間が失われ、市場規模の根拠に使えない。
- **同一性は「系列 + 期間 + 値」。** 取得 URL には期間指定が入るため、URL をそのまま
  同一性に使うと年が変わるたびに同じ数値が新しい観測として湧く。
- **改訂は上書きしない。** 速報値が改訂されたら別の観測として残す。上書きすると
  「いつ何が上方修正されたか」が消える。
- **統計から弱いシグナルを立てない。** 「特許出願件数」という系列名にキーワード判定を
  かけると、年次統計を 1 本取り込んだだけで特許シグナルが 12 件立ち上がる（実測）。
  シグナルとは 1 件の出来事が起きたことであり、集計値はその出来事ではない (§10)。
- **対象セクターは登録時に宣言する。** 系列名にセクター名は現れない
  （"Production in industry, C27" が送配電に効くことは文面から読めない）。

取り込み済み（鍵不要）: World Bank（総固定資本形成・製造業付加価値・研究開発費・
特許出願件数・ハイテク輸出、7 か国）、Eurostat（EU 純発電量、電子・電気機器・建設の
生産指数、月次）。

鍵を入れると有効になるもの: EIA（米国の発電量・電力販売量）、BLS（産業別雇用）。
`FUTURE100_EIA_API_KEY` / `FUTURE100_BLS_API_KEY` を設定して `enabled: true` にする。

未取得: 各国系統運用者 (TSO) の設備投資計画。ENTSO-E 透明性プラットフォームが
最も近い一次情報だが XML のみで JSON 提供が無く、トークン申請と XML コレクタが要る
（`src_entsoe_transparency` に無効のまま登録してある）。

## 技術的負債・既知の制約

| 項目 | 内容 | 影響 |
|---|---|---|
| 経産省 / IEA が 403 | 実行環境からアクセス拒否 | 日本の政策一次情報が欠落中（Phase 2 の最優先課題） |
| 重複判定 O(n²) | 同一実行内の全クラスタ総当たり | 過去データの一括投入時に実用速度を割る |
